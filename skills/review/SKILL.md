---
name: review
description: Review an engineering plan, diff, code or architecture from a general or selected professional perspective, challenging assumptions with evidence and no automatic implementation edits.
---

Interpret ordinary invocation text as optional positional role, `--target=plan|diff|code|architecture`, and `--scope=<artifact or subsystem>`; also accept `--role=<id>`. Default role is `general-reviewer`. Infer the most relevant target from the current request/artifact and repository state, state the selection, and ask only if ambiguity materially compromises correctness. Do not assume a Git baseline or execute invocation text as shell. Vendor syntax belongs in adapters.

Load only the selected perspective from the [core role profiles](../../standards/reviewers/README.md), or the exact profile declared by an explicitly activated pack in `project inspect`. Unknown identifiers are unavailable, never silently substituted. An explicitly requested custom perspective may use stated assumptions without pretending a registered profile exists. Roles change priorities, not evidence thresholds, core gates or permission. Apply evidence standards to summary/strength claims too: unknown delegated/provider behavior remains unknown. Never autoactivate packs for a role.

Establish requirements, intended behavior, artifact/scope and VSD slice criteria/baseline if applicable. For a diff establish base/head or working-tree scope with the user/task; inspect changed files, callers and contracts. An unborn Git repository has no HEAD diff: use an explicitly supplied artifact/snapshot or select code review transparently, not an invented baseline. For plans inspect feasibility, assumptions, dependencies, risks and verification. For code follow relevant call sites and invariants. For architecture inspect boundaries/data flows and actual code/config; use architecture mapping when useful, but a generated diagram is not authoritative evidence.

Read applicable portable standards and approved project/pack requirements. Actively challenge consequential assumptions with realistic failure scenarios, competing explanations and alternatives. Recognize sound decisions; do not invent criticism to appear adversarial. Investigate omissions, regression paths, shared-contract changes and missing verification without treating every possible concern as a defect. Do not read credential stores/environment values or expose secrets in excerpts. For sensitive source/config evidence use sanitized extracts; omit unsafe evidence and state the limitation.

Classify findings as **confirmed defects** or **plausible risks requiring verification**. Each actionable finding includes Critical/High/Medium/Low severity, artifact/file and line where applicable, issue, supporting evidence, concrete failure scenario/consequence, recommended correction, suggested regression/verification, confidence and unresolved uncertainty. For plans cite the relevant section when lines are unavailable. Apply these fields to risks as well as defects. An absent mechanism, unknown contract or hypothetical host behavior is normally a coverage question, not a severity-rated finding. Promote a risk only when a specific evidenced path supports a concrete consequence and actionable verification; do not list missing logging, rate limiting or response uniformity as findings without that basis. Style preferences are not defects without an established standard violation or meaningful consequence. Zero findings is legitimate.

Report concise sections: Review context (role, target/scope, requirements, inspected artifacts); Executive summary (assessment, highest-impact risks, strengths, limits); Findings grouped by severity with defects/risks distinguished; Missing verification; Recommended actions; Coverage limitations. Empty sections can be a sentence. Report actual checks separately from source inspection. Security, performance and visual claims need corresponding evidence: do not claim measured regressions or visible defects without measurements or a rendered interface.

Read [VSD gates](../../standards/vertical-slice-delivery.md) for sliced work: local checks do not establish integration, and failed/missing mandatory gates block acceptance. The reviewer cannot redefine acceptance or waive checks. For high-risk review, consider a native read-only independent context with original requirements, target artifact, relevant context/standards and selected role, without anchoring it on the implementer's full reasoning or previous conclusions. Routine reviews need no delegation; no custom reviewer service is needed.

Read-only by default: do not modify implementation, plans, acceptance criteria or run mutating/application commands. If reproducing a finding requires execution, use only authorized, safe checks; otherwise report the hypothesis. Findings can be implemented in a separately authorized step. Stop for an essential missing artifact/baseline rather than manufacturing findings.
